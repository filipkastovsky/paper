## TL;DR

The v0 server is **Node 22 LTS + Fastify 5 + Zod 4** with `fastify-type-provider-zod`, **`@fastify/swagger` + `@fastify/swagger-ui`** for OpenAPI, **`pino`** logs to Loki, **`@fastify/otel`** traces to Tempo, **`fastify-metrics`** to Prometheus, **Drizzle + drizzle-kit** for data, and **Kubb** to generate the typed client SDK from the OpenAPI spec. Auth is custom **`@fastify/jwt`** with a device-UUID + refresh-token flow. Crons are **5× native K8s CronJob** (per ADR 0009 — see §6 below). No background-job queue in v0.

## Decision

### 2.1 Runtime + framework

- **Node 22 LTS** (active LTS through 2027). Native ESM, native `fetch`, native `--watch`.
- **Fastify 5** — schema-first, plugin-based, mature OpenAPI story, lowest framework overhead in the Node ecosystem with batteries.
- **`fastify-type-provider-zod`** — Zod schemas inferred into route handler types. One source of truth for runtime validation, TypeScript types, and OpenAPI generation.
- **TypeScript strict mode**, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`.

Bun was rejected (brainstorm Q2) on observability and OpenAPI maturity grounds. Hono was rejected on the same axes plus weaker OpenAPI plugin. Elysia was rejected on dual-young-ecosystem risk.

### 2.2 OpenAPI + client codegen

- **`@fastify/swagger` + `@fastify/swagger-ui`** — generates an OpenAPI 3.1 document at `/openapi.json` and serves a Swagger UI at `/docs` (gated behind Authentik in non-dev environments — see ADR 0009).
- **Kubb** — consumes `/openapi.json` and generates, into `packages/api-client/`:
  - TypeScript types (`@kubb/plugin-ts`)
  - Zod schemas for client-side validation (`@kubb/plugin-zod`)
  - Fetch client (`@kubb/plugin-client`)
  - TanStack Query hooks (`@kubb/plugin-react-query`) — feeds ADR 0005
  - MSW handlers (`@kubb/plugin-msw`) — feeds the testing story below

`packages/api-client/` is regenerated by `pnpm gen:api-client` either against a running local server or against a checked-in `openapi.json` snapshot — choice made during implementation; both work.

### 2.3 Data layer

- **Drizzle ORM** — schemas in `apps/server/src/db/schema/`.
- **drizzle-kit** for migrations — `apps/server/drizzle/` directory holds generated SQL.
- **`postgres.js`** as the underlying PG driver (works against CNPG and the `postgres:16` docker-compose container identically).
- **drizzle-zod** to derive Zod schemas from table definitions where it makes sense (e.g. for internal admin endpoints); for public APIs the Zod schema is hand-authored at the route boundary so DB and API can evolve independently.

Migrations run as a Kubernetes Job on each deploy (see ADR 0009).

### 2.4 Logging, tracing, metrics

- **`pino`** structured JSON logging, default level `info` in prod, `debug` in dev.
  - Built into Fastify; no plugin required.
  - In dev, formatted via `pino-pretty`.
  - In prod, JSON lines collected by Grafana Cloud's alloy/promtail and indexed in Loki.
- **`@fastify/otel`** — OpenTelemetry SDK with Fastify-specific request lifecycle hooks. Exports OTLP traces to Grafana Cloud Tempo via the Grafana Cloud OTel endpoint (env-configured).
- **`fastify-metrics`** — exposes `/metrics` in Prometheus format; scraped by Grafana Cloud Prometheus (existing scrape config in `lab/stacks/grafana-monitoring`).
- **No Sentry server SDK in v0.** Server errors surface via pino + Tempo exception spans. Reconsider at v0.1 if source-mapped frontend stack traces become a blocker (see ADR for analytics below).

### 2.5 Authentication

End-user auth follows the product spec's device-UUID flow (§6.1, §11.3):

- `POST /v1/auth/device` — body `{ device_uuid: string }`. Server upserts a `User` row keyed by `device_uuid`, returns `{ access_token, refresh_token, user }`.
- `POST /v1/auth/refresh` — body `{ refresh_token: string }`. Server rotates the refresh token (one-time use, stored hashed in `refresh_tokens`), returns a new pair.
- `access_token` is a JWT signed by `@fastify/jwt` with a 1h expiry, includes `{ sub: user.id, jti }`.
- `refresh_token` is an opaque random 256-bit string, stored hashed in `refresh_tokens` with `user_id`, `expires_at` (90d), `revoked_at`.
- Rotation revokes the old refresh token; reuse of a revoked refresh token revokes the entire family (RFC 6819 §5.2.2.3).
- All routes except `/v1/auth/*`, `/v1/health`, `/openapi.json`, `/docs` require a valid `Authorization: Bearer <jwt>`.

Admin endpoints (none in v0; reserved at `/admin/*`) will be protected via Authentik-Traefik middleware on ingress, not via Fastify-side OIDC. See ADR 0009.

Rejected: Lucia, Better Auth, Clerk — all assume email/OAuth/MFA flows. The device-UUID flow is ~50 lines of custom code.

### 2.6 Crons + background jobs

**v0 has zero non-cron background jobs.** Push notifications send inline from the request that triggers them. Share-card rendering is client-side (spec §7.3). Affiliate webhooks are v0.2.

Crons run as **5× native K8s CronJob** (defined in `lab/stacks/paper/manifests/cronjobs.yaml`):

| CronJob | Schedule | Entrypoint |
|---|---|---|
| `paper-cron-price-ingestion` | `* * * * *` (every minute) | `node dist/jobs/price-ingestion.js` |
| `paper-cron-daily-question-resolve` | `0 0 * * *` (resolves *yesterday's* question) | `node dist/jobs/daily-question-resolve.js` |
| `paper-cron-daily-question-create` | `5 0 * * *` (creates *today's* question, runs after resolver completes) | `node dist/jobs/daily-question-create.js` |
| `paper-cron-leaderboard-recompute` | `*/5 * * * *` | `node dist/jobs/leaderboard-recompute.js` |
| `paper-cron-streak-reaper` | `0 * * * *` | `node dist/jobs/streak-reaper.js` |

The 5-minute gap between `daily-question-resolve` and `daily-question-create` accommodates the resolver finishing before the next day's question is generated. If the resolver overruns 5 minutes (unexpected at v0 scale), the creator job will start anyway; the create job is idempotent on `(date, asset_id)` so a same-day re-run is a no-op.

All five share the same Docker image as `paper-api`; they only differ in `command`. Implementation lives in `apps/server/src/jobs/<name>.ts` — each is a standalone script that imports the same Drizzle client, runs to completion, and exits.

Spec amendment: §11.1's `price_ingestion_cron — every 30s` is amended to **every 60s** to fit native CronJob granularity. Rationale in v0-stack-decisions.md §4.1.

`pg-boss` was considered and **deferred to v0.1**. Cron is a solved problem in K8s; pg-boss earns its weight only when non-cron background work appears (push fan-out at scale, share-card render queue, affiliate webhook delivery).

### 2.7 Rate limiting + idempotency

- `@fastify/rate-limit` with Redis store — 20 trades/min/device, 1 prediction/question/day, IP-based 100 req/min on auth endpoints.
- Idempotency keys (`idempotency_key` columns on Trade and UserPrediction per spec §8.2, §8.4) enforced via unique index + insert-on-conflict-do-nothing semantics. Replay returns the previously-stored result.

### 2.8 Push notifications

- `web-push` library, VAPID keys generated once and stored as a Kubernetes secret.
- Subscriptions stored in a `push_subscriptions` table keyed by `user_id` + endpoint.
- Send-side is inline for v0 — when an event triggers a push (streak-at-risk reaper finds at-risk users; daily question goes live), the cron job iterates and sends synchronously. Volume at v0 scale (≤10k DAU during weeks 1–8) is small enough that this is fine.
- Reconsider at v0.1 once DAU > 10k or send-fanout times exceed CronJob runtime budgets.

### 2.9 Analytics + frontend errors + session replay

- **PostHog** (already specified) with the JavaScript SDK on the client. Single SDK provides:
  - Event analytics (the full taxonomy from spec §9)
  - Session replay (debug onboarding drop-off)
  - Frontend error tracking (PostHog Errors product)
- Server has no PostHog SDK — analytics-relevant server events fire via the client SDK with the user's session.
- Sentry is **not** added in v0. PostHog Errors covers frontend; pino + Tempo cover backend. Source-map upload is configured for PostHog so production stack traces are de-minified.

### 2.10 Testing

- **Vitest** for unit + integration tests on the server. Database integration tests run against a `postgres:16` docker-compose container with a per-test schema.
- **Playwright** for E2E on the PWA. Single mobile viewport in v0 (390×844, iPhone 14). Headless in CI; headed for local debugging.
- **MSW** — Kubb generates handlers from the OpenAPI spec. Web app tests use these for component-level integration; no hand-written fixtures.
- Coverage tracked but no threshold gate in v0 — solo dev, fast iteration; thresholds reconsidered at v0.1 when cohort retention data demands defending the surface.

## Rationale

Per founder priority order (brainstorm Q2): setup speed, type safety, OpenAPI, observability, maturity. Fastify is the only single answer that doesn't trade off against any of the five.

Drizzle is chosen over Prisma on three counts: lighter runtime (no query engine binary), TypeScript-native schema (no separate DSL), and `drizzle-zod` integration that aligns with the Zod source-of-truth pattern.

Kubb is chosen over `openapi-typescript` + `openapi-fetch` because of the bundled TanStack Query + Zod + MSW codegen — the entire client data layer lights up from one OpenAPI document, with no additional plumbing.

PostHog covers analytics + replay + errors with one SDK and one bill, matching the spec's vendor minimisation principle. Splitting frontend errors into Sentry is reconsidered only when the UX of stack-trace inspection becomes a bottleneck.

Cron-only-no-queue is a deliberate scope cut. The cost of pg-boss is small but non-zero; deferring it preserves "drop a CronJob" as the simplest possible operation when v0 needs a new periodic task. Adding pg-boss is a half-day of work when the first non-cron job arrives.

## Consequences

### Positive

- **One typed contract** flows from Drizzle table → Fastify Zod schema → OpenAPI → Kubb → React hook. Renaming a field is a single PR with TypeScript guiding the change.
- **Free observability** on day one — pino lines in Loki, OTel traces in Tempo, Prometheus metrics scraped — because Grafana Cloud is already wired.
- **Cron architecture matches the platform.** No queue infrastructure to babysit; CronJob status is `kubectl get jobs`.
- **Auth code is small and inspectable.** No library ceremony for a flow we need to keep simple.

### Negative / accepted

- **No automatic background job retries beyond CronJob's `backoffLimit`.** Jobs that fail mid-run leave partial state. Mitigation: each job script is idempotent (re-running produces the same result) and writes its progress checkpoints to Postgres; the next CronJob tick picks up where the previous left off. Strict at-least-once semantics; jobs design for it.
- **Inline push send can starve a CronJob** if subscription count grows unexpectedly. Mitigation: monitor CronJob runtime in Grafana; flip to pg-boss when p99 runtime > schedule period.
- **PostHog Errors UX is decent but not Sentry-grade.** Accepted; reconsider at v0.1.
